## 引言：CSAE 立项答辩的最大问题

本团标在 2026 年 6 月底答辩时，评审专家最可能问出的一句话是：

> "你这个标准，和正在起草的安全事件数据交互 GB/T 国标（在研），是什么关系？"

这是一道命门题。回答不好，立项被毙；回答好了，整个标准的价值反而因为对照而凸显。本文系统回答这个问题，分四步：

1. 精读 GB 讨论稿做什么 / 不做什么
2. 说明 本团标做什么 / 不做什么
3. 交集分析（哪里看似重叠，哪里完全不交）
4. 切割逻辑与协同效应

## 第一部分：GB 讨论稿到底管什么

### 1.1 范围（Scope）一句话概括

《智能网联汽车安全事件数据交互与管理系统技术规范》推荐性国家标准（在研）管的是：

> 车载终端 → 企业平台 → 国家平台 之间，安全事件数据的采集、上报、报告（数据格式 / 通信协议 / 加密 / 补发）。

注意三个关键限定：

- 监管的是"数据通道"，不是"运营行为"
- 覆盖 L2 组合驾驶辅助 + L3+ 自动驾驶（不限于 L4）
- 监管对象是车辆制造商 + 企业平台承建方 + 国家平台运维方

### 1.2 GB 讨论稿的章节结构与技术内容

| 章 | 内容 | 技术实质 |
|---|---|---|
| 1 | 范围 | 数据通道的范围限定 |
| 2 | 规范性引用文件 | 引用通信、加密、车联网相关 GB |
| 3 | 术语和定义（18 项） | 全部围绕"数据通道"展开 |
| 4 | 系统架构 | 车-企业-国家三层架构 |
| 5 | 功能要求 | 数据采集 / 传输 / 补发，平台注册 / 接收 / 上报 / 报告 / 存储 |
| 6 | 通信协议与数据格式 | TLS 1.2+ / SM2 / SM4 |
| 7 | 试验方法 | 数据通道测试 |
| 8 | 同一型式判定 | 型式认证 |
| 9 | 实施 | 推荐实施日期 |
| 附录 A | 事件数据上报（规范性） | 11 种事件类型字节定义 |
| 附录 B | 事件数据报告（规范性） | 48h / 30d / 年度报告 |

GB 讨论稿的核心术语有 8 个：

- 智能网联汽车安全事件数据交互与管理系统
- 车载终端
- 企业平台
- 国家平台
- 事件数据
- 安全事件数据
- 在线升级
- 注册

这 8 个术语构成了 GB 的全部技术语义空间。所有内容都围绕"如何把数据从车端经企业平台送到国家平台并完成报告"展开。

### 1.3 GB 讨论稿的数据元素（核心管控对象）

GB 讨论稿规定了四个层级的数据元素：

| 层级 | 数据内容 | 字段数 |
|---|---|---|
| 第 1 层 | 车辆备案信息 | 17 项（VIN / ICCID / 合格证编号 / 数据记录系统硬件软件版本等） |
| 第 2 层 | 可升级控制器备案信息 | 控制器 ID 0x01-0xFF + 网安事件 ID |
| 第 3 层 | 实时上报数据 | 4 类事件类型 × 各类详细字节 |
| 第 4 层 | 周期性报告 | 关键事件 48h 报告 + 30 天更新 + 年度报告 |

第 3 层是最值得细看的。其中"自动驾驶系统事件"枚举了 11 种：

```
0x00  激活
0x01  退出
0x02  介入请求
0x03  启动 MRC（最小风险机动）
0x04  严重失效
0x05  碰撞
0x06  碰撞风险
0x07  远程协助
0x08-0x0A  其他
```

碰撞事件的附录 A.4 ~ A.9 详细规定了：

- 车辆动态信息（57 字节）
- 系统运行信息（112 字节）
- 行车环境结构体（每目标 100 字节）
- 驾驶员状态（22 字节）

这是一份典型的"数据规范型"标准（data specification），其管理逻辑是：发生一个事件 → 按字节格式封装 → 通过加密通道上报 → 国家平台存储与统计。

### 1.4 GB 讨论稿不管什么

精读 GB 讨论稿后，可以列出该标准明确不管的内容：

| 不管的内容 | 说明 |
|---|---|
| 谁来处置异常 | 数据上报后企业内部如何响应，GB 不涉及 |
| 远程操作员的工作流程 | Remote Driver / Remote Assistant 的岗位职责，GB 不定义 |
| 跨企业责任划分 | OEM / 运营平台 / 车队所有者之间的责任边界，GB 不涉及 |
| 运营 KPI | MTTR、AI 处置率、误升级率等运营指标，GB 不涉及 |
| 与执法消防医疗的协同 | 第一响应者交互流程，GB 不涉及 |
| 多种运营模式 | Robotaxi / OEM 订阅 / 公交 / 配送等模式分类，GB 不涉及 |
| 异常场景的细分 | E1 道路施工 / E5 紧急地理围栏等场景分类，GB 不涉及 |

这一长串"不管的内容"，正是 本团标的领地。

## 第二部分：本团标到底管什么

### 2.1 范围（Scope）一句话概括

《智能网联汽车 高度自动驾驶车辆运营管理异常事件处置规范》（CSAE 团标）管的是：

> L4 自动驾驶车辆运营过程中异常事件的分类、决策架构、责任划分、KPI 评价与第一响应者交互的参考架构。

注意三个关键限定：

- 管的是"治理框架"，不是"数据通道"
- 仅覆盖 L4（不涉及 L0-L3）
- 监管对象是运营企业内部的决策流程与组织架构

### 2.2 本团标的章节结构

| 章 | 内容 | 技术实质 |
|---|---|---|
| 1 | 范围 | 治理框架的适用范围 |
| 2 | 规范性引用文件 | 引用 ISO 22737 / SAE J3016 / GB 讨论稿等 |
| 3 | 术语和定义（35+ 项） | 围绕运营治理展开 |
| 5 | 总体框架 | 参考架构总览图 |
| 6 | 10 种 L4 运营模式 | M1-M10 模式分类 |
| 7 | 29 子场景的异常事件分类 | A1-F4 场景分类 |
| 8 | 三层决策参考架构 | L1 AI 自主 / L2 AI 辅助 + 人工 / L3 远程驾驶 / 线下 |
| 9 | 责任矩阵 | 10 模式 × 3 层 × 7 维度 |
| 10 | 16 项 KPI 评价基准 | MTTR / AI 处置率 / 监管反馈合规等 |
| 11 | FRIP 模板 | 第一响应者交互计划 |

本团标的核心术语涵盖：

- 运营异常（vs GB 的"安全事件"）
- 三层决策（L1 / L2 / L3）
- 远程运营中心（ROC）
- 远程驾驶员（Remote Driver）
- 远程协助员（Remote Assistant）
- 紧急地理围栏（Emergency Geofencing）
- Override 系统
- Avoidance Area
- 第一响应者交互计划（FRIP）
- 监管反馈维度
- 运营模式（Operating Mode）

这些术语在 GB 讨论稿中完全不出现，因为它们属于运营治理的语义空间，不属于数据通道。

### 2.3 本团标不管什么

| 不管的内容 | 原因 |
|---|---|
| 数据通信协议 / 字节格式 | 由 GB 讨论稿规定 |
| 加密算法 / 密钥管理 | 由 GB 讨论稿与 ISO/SAE 21434 规定 |
| 国家平台的注册与对接 | 由 GB 讨论稿规定 |
| 48h / 30d / 年度报告格式 | 由 GB 讨论稿附录 B 规定 |
| L4 车辆型式认证 | 由《搭载高度自动驾驶系统（无驾驶人）乘用车技术要求及测试方法》规定 |
| 单车 SOTIF 论证 | 由 ISO 21448 及对应中国 SOTIF 标准规定 |

本团标主动让出这些内容，恰好填入了 GB 讨论稿与 L4 整车标准之间的空白。

## 第三部分：交集分析——哪里看似重叠，哪里完全不交

### 3.1 交集矩阵

把 GB 讨论稿涉及的内容与 本团标涉及的内容做交集，结果如下：

| 主题领域 | 仅 GB | 真重叠 | 仅 ROAM |
|---|:---:|:---:|:---:|
| 车端→国家平台数据通道 | ✓ | | |
| 字节级数据格式 | ✓ | | |
| 加密协议（TLS / SM2 / SM4） | ✓ | | |
| 车辆备案信息 17 项 | ✓ | | |
| 控制器 ID 0x01-0xFF | ✓ | | |
| 48h / 30d / 年度报告 | ✓ | | |
| 国家平台对接 | ✓ | | |
| ADS 事件类型枚举（11 种作为待上报数据） | ✓ | | |
| 同样的 ADS 事件作为运营异常输入信号 | | △ | |
| ROC 内部三层决策架构 | | | ✓ |
| 10 种运营模式 | | | ✓ |
| 29 子场景分类 | | | ✓ |
| 跨企业责任矩阵 6 维 + 监管反馈外层 | | | ✓ |
| 16 KPI 评价基准 | | | ✓ |
| FRIP 模板 | | | ✓ |
| Avoidance Area / Override System | | | ✓ |
| 分级运营限制（监管反馈维度） | | | ✓ |
| Remote Driver / Remote Assistant 岗位定义 | | | ✓ |

### 3.2 唯一一处真重叠：ADS 事件类型枚举

整个交集表里，只有一处可以标记为"重叠"——ADS 事件类型枚举。GB 讨论稿附录 A.5 列出了 11 种 ADS 事件，其中至少 4 种与 ROAM 场景分类对应：

| GB 事件类型 | GB 编码 | ROAM 场景对应 | ROAM 场景编码 |
|---|---|---|---|
| 介入请求 | 0x02 | 远程协助介入 | A2 |
| 启动 MRC | 0x03 | 最小风险状态进入 | C3 |
| 远程协助 | 0x07 | 远程驾驶接管 | A1 / A2 |
| 碰撞风险 | 0x06 | 紧急避撞决策 | B2 |

但这种重叠不构成冲突，因为两个标准对同一事件的处理方式截然不同：

| 维度 | GB 视角 | ROAM 视角 |
|---|---|---|
| 把事件当作什么 | 待上报的数据 | 待处置的运营异常输入信号 |
| 关心什么 | 字节格式 / 时间戳 / 上报通道 | 谁处置 / 何时处置 / 用什么 KPI 评价 |
| 输出什么 | 数据进入国家平台 | 决策动作 + KPI 记录 + 责任归属 |
| 抽象层级 | 字节级 | 架构级 |
| 监管对象 | 车辆制造商 + 平台承建方 | 运营企业内部 |

打个比方：GB 关心"病历表格的字段格式"，ROAM 关心"医生看到病历后如何分诊治疗"。同一个病人，两个标准在不同层面发挥作用，不构成冲突。

### 3.3 本团标如何处理这处重叠

本团标在第 7 章（场景分类）和第 11 章（FRIP）中，对应到 GB 事件类型时采用以下原则：

- 不重新定义 GB 已规定的字节格式或时间戳精度
- 不重新规定 GB 已要求的上报频率或加密协议
- 在术语对照表（附录 C）中列出 ROAM 场景代码与 GB 事件编码的映射关系
- 仅规定运营决策层面的处置流程、责任划分、KPI 测量

这种处理方式确保了两个标准在同一事件上的语义不冲突。

## 第四部分：四类"看似重叠实则互补"的具体场景

为了让评审专家清楚看到两个标准的协同关系，下面用四个具体场景展示。

### 场景 1：远程协助介入（GB 事件 0x07）

车端发生：L4 车辆遇到复杂路口无法自主决策，自动触发远程协助请求。

GB 视角：

- 车载终端记录事件时间戳
- 按附录 A.5 字节格式封装事件数据
- 通过加密通道上报到企业平台
- 企业平台 48 小时内向国家平台上报
- 30 天内更新事件处置结果

ROAM 视角：

- 事件触发 ROAM 三层决策架构的 Layer 2 流程
- ROC 内 Remote Assistant 在 30 秒内响应（KPI 9）
- AI 给出决策建议并附置信度
- Remote Assistant 评估并确认 / 修改 / 升级
- 决策传回车端执行
- 全流程数据按 ROAM KPI 模板记录到企业 ROC 系统

协同关系：GB 关心"事件已上报到国家平台"，ROAM 关心"事件被 ROC 在 30 秒内有效响应"。两者关心的是同一事件的不同侧面。

### 场景 2：批量系统瘫痪（如武汉萝卜快跑事件）

车端发生：100 辆 L4 车辆在高架路段同时熄火，无法自主恢复。

GB 视角：

- 每辆车产生"严重失效"事件（0x04）
- 100 个事件按字节格式上报到企业平台
- 企业平台聚合后按 48 小时关键事件报告通道上报国家平台

ROAM 视角：

- 触发 ROAM 场景 D1（批量系统故障）
- 进入 Layer 3 远程驾驶 / 线下派人流程
- 责任矩阵第六维度（Avoidance Area）启动：执法部门可指定紧急地理围栏
- 责任矩阵第七维度（监管反馈）启动：DMV-style 分级运营限制评估
- KPI 14（监管限制合规时限）开始计时
- FRIP 模板第 9 节（车辆移动协调）：交警与 ROC 协商集中拖移路径

协同关系：GB 解决"国家平台知道了发生什么"，ROAM 解决"运营企业、执法部门、保险公司之间如何协同处置"。

### 场景 3：远程驾驶员在境外操作（Markey 报告关注点）

情境：Waymo 海外 Remote Assistant（菲律宾，约占 50%）操作美国境内车辆。

GB 视角：

- GB 不关心 Remote Driver / Remote Assistant 的国籍 / 资质 / 物理位置
- 只要数据按规上报，即合规

ROAM 视角：

- 第 8 章（三层决策架构）规定 Remote Driver 必须持有运营所在国驾照
- 第 9 章（责任矩阵）的"法律责任"维度规定跨境操作的责任归属
- 第 10 章 KPI 12（操作员资质合规率）= 100% 强制
- 附录 A 与加州 DMV § 227.38 / § 227.40 对照

协同关系：GB 不涉及操作员资质问题，本团标补足这一空白，与加州 DMV 形成跨太平洋监管协同。

### 场景 4：分级运营限制（加州 DMV § 227.46）

情境：某 Robotaxi 运营商连续 30 天 KPI 1（MTTR）严重超标。

GB 视角：

- 不涉及。GB 仅规定数据上报，不规定监管处置。

ROAM 视角：

- 责任矩阵第七维度（监管反馈维度，v1.2 新增）
- 触发 5 档分级处置之一（整改 / 日常限制 / 强制人员 / 立即限制 / 完全吊销）
- KPI 14（监管限制合规时限 ≤ 24h）/ KPI 15（解除申请周期 ≤ 30 天）/ KPI 16（限制复发率 < 10%）
- 与公安部道研中心牵头制定的执法对接细则联动

协同关系：GB 是数据合规的入口，ROAM 是治理闭环的出口，两者共同构成"数据合规 → 治理评估 → 监管处置"的完整链路。

## 第五部分：双层支撑与协同效应

### 5.1 标准化体系图

```
┌─────────────────────────────────────────────────────────────┐
│                   L4 自动驾驶商业化运营                          │
├─────────────────────────────────────────────────────────────┤
│  治理层（运营行为）                                              │
│  ┌─────────────────────────────────────────────────────────┐│
│  │  本团标（CSAE T/CSAE XXX-2026）                       ││
│  │  - 运营异常分类                                           ││
│  │  - 三层决策架构                                           ││
│  │  - 责任矩阵                                              ││
│  │  - KPI 评价基准                                           ││
│  │  - FRIP 模板                                             ││
│  └─────────────────────────────────────────────────────────┘│
├─────────────────────────────────────────────────────────────┤
│  数据层（数据通道）                                              │
│  ┌─────────────────────────────────────────────────────────┐│
│  │  GB/T 国标（在研）《安全事件数据交互与管理系统技术规范》            ││
│  │  - 车端→企业平台→国家平台数据通道                         ││
│  │  - 数据格式 / 通信协议 / 加密                             ││
│  │  - 事件类型枚举 / 字节定义                                ││
│  │  - 报告周期与频率                                         ││
│  └─────────────────────────────────────────────────────────┘│
├─────────────────────────────────────────────────────────────┤
│  车辆层（型式认证）                                              │
│  ┌─────────────────────────────────────────────────────────┐│
│  │  CSAE《无驾驶人 L4 乘用车技术要求及测试方法》             ││
│  │  - 车辆本体的安全要求                                     ││
│  │  - 测试方法与验证                                         ││
│  └─────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────┘
```

三层从下到上：车辆本体合规（型式认证）→ 数据合规（GB/T 国标（在研））→ 治理合规（本团标）。三者共同构成 L4 商业化运营的完整合规链。

### 5.2 互为支撑的具体场景

| 协同关系 | 说明 |
|---|---|
| GB 是 ROAM 的数据基础 | ROAM KPI 测量所需的事件数据，按 GB 规范从车端采集上报，确保 KPI 可被独立审计 |
| ROAM 是 GB 的治理出口 | GB 数据进入国家平台后的统计与监管反馈，可参照 ROAM 责任矩阵第七维度的分级处置机制 |
| ROAM 给 GB 数据增加业务语义 | GB 的 11 种 ADS 事件枚举，通过 ROAM 场景分类映射到具体的运营场景 |
| GB 给 ROAM 提供合规边界 | ROAM KPI 不重新定义数据格式，凡涉及对外通信均引用 GB 规范 |

### 5.3 起草协同建议

为避免起草过程中两个标准的相互冲突，建议：

- ROAM 起草组在制定术语时，主动避开 GB 已定义的 8 个核心术语
- ROAM 不重新定义 ADS 事件的字节格式，附录 C 仅给出与 GB 编码的对照表
- ROAM 在每章前言注明"本章不涉及 GB XXX 规定的 XXX"
- 通过 CAICV 联盟与 GB 起草组建立沟通机制，互相评审跨标准接口

## 第六部分：与国际同类标准的对比

为了进一步证明 本团标定位的合理性，与三份国际标准做对比：

### 6.1 ISO 22737（LSAD 低速自动驾驶）

ISO 22737 是 ISO/TC 22/SC 33/WG 9 发布的低速自动驾驶标准，包含"无人驾驶运营调度员"角色定义。它定位为参考架构 + 部分功能要求的混合型标准，与 本团标的"参考架构"定位接近。本团标可借鉴 ISO 22737 的章节组织方式。

### 6.2 SAE J3016（驾驶自动化分级）

SAE J3016 明确规定其不定义 teleoperation（远程操作）。这正是 本团标存在的空间——SAE J3016 拒绝定义的远程操作内容，由 本团标在中国语境下补足。

### 6.3 加州 DMV Article 3.7

加州 DMV Article 3.7（Express Terms 2026）是法规（regulation），不是技术标准（standard），但其内容覆盖了 本团标的核心命题：Remote Driver / Remote Assistant 二分、14 项安全档案、§ 227.46 分级运营限制、§ 227.42(i) FRIP 模板等。本团标在术语和阈值层面与加州 DMV 对齐，但作为参考架构而非要求规范，不构成法规对法规的对峙。

### 6.4 国际定位结论

本团标在国际上是首部以"L4 远程运营与异常管理"为专门对象的"参考架构型"标准。这一定位与 GB/T 国标（在研）完全互补：GB 是中国监管的"数据入口"，ROAM 是中国行业的"治理框架"，加州 DMV 是美国监管的"合规基准"，三者共同构成 L4 自动驾驶在跨太平洋监管语境下的完整体系。

## 结语：一句话定位

如果立项答辩只能讲一句话，建议这样讲：

> GB 讨论稿规定数据怎么上报，本标准规定数据上报后企业怎么处置异常。前者管字节格式，后者管决策架构。两者是"数据通道 × 运营治理"的双层支撑，不构成冲突。

这一句话写入：

- 立项申请表 B.8 立项背景章
- 立项答辩 PPT 第 3.5 章首页
- 标准草案前言第二段
- 标准草案引言第三段
- 公开发声（公众号 / LinkedIn）的开篇

每一处都不要变更措辞。一致性比修辞重要。

### 标准草案前言示例

> 本文件不是《智能网联汽车 安全事件数据交互与管理系统技术规范》的替代或补充。后者规定了车载终端→企业平台→国家平台之间安全事件数据的采集、上报、报告的数据格式、通信协议和管理流程，关注的是数据通道与监管接口。本文件提供 L4 自动驾驶车辆运营过程中异常事件的运营治理参考架构，关注的是异常发生后，运营企业内部由谁、何时、用什么方式做出处置决策。两份标准在抽象层级、监管对象、技术内容上不构成重叠，共同构成 L4 商业化运营的"数据合规 × 运营治理"双层支撑。

### 标准草案引言示例

> GB 讨论稿解决"什么数据要上报"的问题，正在制定的 ADS 安全要求 GB/T 国标（在研）解决"车辆本身要安全到什么程度"的问题，而本文件回答两者之间的运营治理空白：当一辆已通过型式认证、已按规定上报数据的 L4 车辆，在实际运营中发生异常时，企业的远程运营中心应该如何分级处置，谁承担什么责任，用什么 KPI 评价。本文件以参考架构（reference architecture）而非技术要求（requirements specification）的形式提出，主要服务于运营企业的内部治理与跨企业的协作框架建设。
